## Изменившийся контракт PDF и требования runtime

Для Builder Resume требуется доступный React renderer через корректный `FRONTEND_URL`. Если URL не задан либо React-печать не удалась, endpoint экспорта возвращает **HTTP 503, код `PDF_RENDERER_UNAVAILABLE`**. Неполный или небезопасный резервный PDF не выдаётся как успешный файл.

Toolbar сообщает, что PDF временно недоступен, резюме сохранено и можно повторить попытку позднее либо экспортировать DOCX. Ошибка renderer не выдаётся за успешное скачивание. Внутренние адреса и диагностические подробности не передаются пользователю. Настройки production/deploy в рамках этой задачи не менялись; доступность `FRONTEND_URL` должна быть обеспечена средой запуска.

PDF content E2E использует `pdftotext` из Poppler, доступный в PATH. Отсутствие программы завершает проверку явной ошибкой, а не пропуском assertions. Новая зависимость в manifests/lockfile не добавлена.

## Независимый fix-loop и окончательная проверка — PASS

Первый свежий Sol QA и независимая Astra выявили P1: старое top-level сохранение могло удалить успешно созданную позже строку, потому что structural reconcile сравнивал старый snapshot с текущим набором server IDs. Refetch в промежутке мог закрепить пустую структуру и показать Saved. Замечание не отклонено и не замаскировано зелёной общей suite.

Родитель выявил риск повторного CREATE; developer воспроизвёл его двумя управляемыми тестами: новая строка с ещё незавершённым CREATE могла быть создана повторно из старого сохранения. Следующий свежий Sol QA нашёл второй P1: Undo pending CREATE → завершение CREATE с компенсационным DELETE → Redo возвращал строку локально, но не восстанавливал её на сервере.

Все три сценария исправлены developer:

- Для каждой поставленной в очередь ревизии фиксируется scope известных серверных и pending-local IDs; structural reconcile учитывает более новое live/outgoing намерение и не удаляет строки, появившиеся после старого снимка.
- Зарегистрированный pending CREATE ожидается; после него разрешаются alias IDs, поэтому reconcile не запускает второй CREATE той же строки.
- Серверный ID усваивается во всех ревизиях истории **до** выхода через ветку компенсационного удаления. Redo после компенсации действительно восстанавливает строку удалённо.

В [регрессиях очереди и истории](../../fe/src/features/resume-builder/lib/resumeDocumentSync.test.ts) добавлены **9 управляемых сценариев**:

| Группа | Число | Проверяемый результат |
|---|---:|---|
| Новый успешный CREATE против старой записи и refetch | 2, active/outgoing | Новая строка остаётся локально и удалённо, лишний DELETE отсутствует |
| Scope старой ревизии и явное структурное намерение | 3 | Поздний CREATE сохраняется после смены документа; Undo pending CREATE удаляет явно отменённую строку; более новый outgoing Redo имеет приоритет над старым Undo |
| Pending CREATE против старых top-level writes | 2, active/outgoing | CREATE выполняется ровно один раз, строка не дублируется |
| Redo после компенсации pending CREATE | 2, active/outgoing | После Undo/компенсационного DELETE Redo создаёт строку удалённо; повторная загрузка модели через reconcileLoadedResume сохраняет строку |

В последних двух наблюдались два CREATE, один намеренный DELETE, восстановление строки server-2.
